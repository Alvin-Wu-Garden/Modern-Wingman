# 開發、程式碼生成與測試模式固定指令

## 一、核心執行原則

目前系統仍處於開發與測試階段，尚未正式上線。進行需求實作、Bug 修正、程式碼重構、資料庫調整及測試時，必須遵守以下原則：

1. 允許進行破壞性重構。
2. 不需要維持舊版 API、舊資料庫 Schema、舊類別介面或向下相容性。
3. 優先產生容易閱讀、容易維護、可以直接執行的最小必要程式碼。
4. 關鍵設計意圖、商業規則及非直覺邏輯，必須提供繁體中文註解。
5. 不得以大量註解、抽象層、設計模式或額外框架掩蓋過度設計。
6. 只實作目前需求明確要求的內容，不為假設性的未來需求預先設計。
7. 測試完成後，必須清除所有自動測試產生的資料及檔案。
8. SQLite 只允許保留人工問答功能所需的既有 PAT 或 Credential。
9. Neo4j 測試完成後不得保留任何測試節點與關係。
10. 自動測試完成後，系統必須回到可直接進行人工點擊與問答測試的乾淨狀態。
11. 不得連線、修改或刪除正式環境及共用環境的資料。
12. 不得洩漏 PAT、Token、Authorization Header 或其他機密資訊。
13. 不得聲稱已執行實際上未執行的建置、測試或驗證。
14. 無法完成的驗證必須清楚標示為「尚未驗證」。

---

# 第一部分：開發與重構規則

## 二、破壞性重構原則

1. 可以重新命名、移動、刪除或重新設計現有模組。
2. 可以調整 API Endpoint、Request、Response、DTO、資料表及 Neo4j 圖結構。
3. 可以刪除已不再需要的舊版程式碼。
4. 可以刪除舊 Migration，重新建立新的初始 Migration，但僅限尚未正式上線的開發階段。
5. 修改後必須同步更新：

   * Dependency Injection 註冊
   * API Contract
   * 設定檔
   * Migration
   * SQLite Schema
   * Neo4j Schema
   * 索引與約束
   * 測試
   * 註解
   * 相關文件
6. 不要為尚未正式使用的舊結構增加相容層。
7. 不得同時保留新舊兩套實作，除非需求明確要求過渡期相容。
8. 重構後不再使用的類別、方法、設定、套件及檔案必須刪除。
9. 不得留下無法實際執行、未被呼叫或未完成註冊的程式碼。
10. 所有破壞性變更都必須在結果報告中明確列出。
11. 破壞性重構不得破壞人工問答功能使用的既有 PAT。
12. 若重構 Credential 儲存方式，必須明確處理既有 PAT 的保留或安全遷移。

---

## 三、最小必要變更原則

實作時必須遵守：

* KISS：保持設計簡單。
* YAGNI：不實作尚未需要的功能。
* 最小必要變更：只修改完成目前需求所需的範圍。
* 一致性優先：優先沿用專案現有且合理的架構與程式風格。
* 可讀性優先：程式碼應讓 Reviewer 能直接理解。
* 可刪除性優先：開發階段不保留沒有實際用途的相容程式碼。

實作前應先判斷：

1. 是否可以直接修改現有程式碼？
2. 是否真的需要新增類別？
3. 是否真的需要新增 Interface？
4. 是否真的需要建立新的專案或模組？
5. 是否已經存在可重用的類別或方法？
6. 是否可以使用現有套件完成？
7. 是否能以更少的程式碼達成相同結果？
8. 是否正在為尚未出現的需求預留擴充點？
9. 是否會產生沒有實際呼叫者的程式碼？
10. 是否會增加不必要的維護成本？
11. 是否可以直接刪除舊實作，而不是建立額外的相容層？
12. 是否會影響 SQLite 中必須保留的 PAT？

若簡單方案已足以滿足目前需求，必須採用簡單方案。

# 第二部分：程式碼生成與設計約束

## 四、避免過度設計

不得因為「未來可能會用到」而加入大量抽象設計。

除非有明確需要，否則不要新增：

* Factory
* Builder
* Strategy
* Mediator
* Event Bus
* Plugin System
* 通用工作流程引擎
* 自訂 ORM
* 自訂 Dependency Injection Container
* 不必要的 Repository Wrapper
* 不必要的 API Client Wrapper
* 不必要的 Facade
* 沒有實際需求的擴充點
* 僅有一個實作且沒有隔離價值的 Interface
* 需求未要求的快取層
* 需求未要求的訊息佇列
* 需求未要求的背景工作
* 需求未要求的通用設定框架

不得：

1. 為簡單功能強制套用設計模式。
2. 為了形式上的 Clean Architecture 拆出大量只有少數程式碼的專案。
3. 建立只有單一呼叫者且沒有隔離價值的 Service。
4. 建立沒有實際使用者的通用平台。
5. 建立需求未要求的動態設定機制。
6. 建立需求未要求的 Plugin 架構。
7. 引入新的框架或 NuGet 套件來解決現有程式碼可以直接完成的問題。
8. 為每一個類別機械式建立 Interface。
9. 將簡單流程拆成大量微小方法，導致理解時必須在多個檔案間跳轉。
10. 為了「看起來專業」而增加無實際價值的程式碼。
11. 為目前不存在的第二種資料庫、LLM Provider 或儲存方式建立抽象層。
12. 為不確定是否會發生的需求加入大量預留欄位或設定。
13. 產生未註冊、未呼叫或無法從現有流程進入的程式碼。
14. 使用 TODO 取代目前需求中應完成的實作。

---

## 五、允許新增抽象層的條件

只有符合下列至少一項條件時，才應新增抽象層：

1. 已經存在兩個以上的實際實作。
2. 需要隔離 SQLite、Neo4j、HTTP、LLM Provider 或檔案系統，以利測試。
3. 需要分離具有不同生命週期的元件。
4. 需要避免核心商業邏輯直接依賴外部基礎設施。
5. 現有重複程式碼已造成明確維護問題。
6. 新增抽象層可以實際降低耦合，而非只是增加檔案數量。
7. 專案現有架構已採用相同模式，維持一致性較容易維護。
8. 抽象層有明確的呼叫者及測試價值。

新增抽象層時，必須說明：

* 為什麼需要它。
* 哪些類別會使用它。
* 它解決了什麼實際問題。
* 為什麼不能直接使用較簡單的實作。
* 若不新增這個抽象層，會產生什麼具體問題。

無法清楚回答上述問題時，不應新增該抽象層。

---

## 六、程式碼數量控制

1. 優先修改既有程式碼，不得無理由新增大量檔案。
2. 每個新增類別、介面、方法、設定或套件，都必須有明確用途。
3. 新增項目必須存在實際呼叫者。
4. 不得產生未被使用的類別、方法、欄位及設定。
5. 不得保留沒有實際用途的範例程式碼。
6. 不得建立內容高度相似的 DTO、Model、Request 或 Response。
7. 可以共用既有型別時，不得建立重複型別。
8. 小型且只使用一次的邏輯，不必強制抽成獨立 Service。
9. 方法應具有清楚責任，但不得為了縮短方法而過度拆分。
10. 不得產生只有轉呼叫另一個方法、但沒有驗證、轉換或隔離價值的 Wrapper。
11. 不得建立尚未被任何流程使用的預備實作。
12. 產生程式碼後，應主動刪除：

    * 未使用的 using
    * 未使用的欄位
    * 未使用的方法
    * 未使用的類別
    * 未使用的套件
    * 無效的 Dependency Injection 註冊
    * 過時設定
    * 重構後殘留的舊實作
    * 已失效的測試
    * 已失效的註解

---

## 七、命名與可讀性

1. 類別、方法及變數名稱必須表達實際業務意圖。
2. 除通用縮寫外，不得使用難以理解的縮寫。
3. 布林值應使用：

   * `Is`
   * `Has`
   * `Can`
   * `Should`
4. 方法名稱應明確表達是否會：

   * 查詢資料
   * 修改狀態
   * 刪除資料
   * 建立資料
   * 呼叫外部服務
   * 清理測試資料
5. 具有破壞性的操作，方法名稱必須清楚，例如：

   * `DeleteTestDataAsync`
   * `ResetNeo4jDatabaseAsync`
   * `CleanupTestArtifactsAsync`
   * `DeleteConversationHistoryAsync`
6. 避免使用責任不明確的名稱：

   * `Helper`
   * `Manager`
   * `Utility`
   * `Common`
   * `Processor`
7. 優先讓程式碼本身可讀，再使用註解補充設計原因與限制。
8. 不得依靠大量註解彌補命名不清或結構混亂。
9. 方法名稱若包含 `Delete`、`Reset`、`Clear` 或 `Cleanup`，必須能從名稱或註解判斷其影響範圍。
10. 保存 PAT 的程式碼必須使用清楚名稱，不得與一般測試資料清理邏輯混合。

# 第三部分：繁體中文註解規則

## 八、註解語言要求

1. 生成或修改程式碼時，必要註解一律使用繁體中文。
2. 不得使用簡體中文。
3. 技術名詞可以保留英文，例如：

   * Dependency Injection
   * CancellationToken
   * Repository
   * Transaction
   * Migration
   * BackgroundService
   * Feature Flag
   * Credential
   * Endpoint
4. 註解必須清楚、直接，避免過度冗長。
5. 註解必須與實際程式碼保持一致。
6. 修改程式碼時，必須同步更新相關註解。
7. 不得保留失效、過時、誤導或與實作不符的註解。
8. 註解應補充設計原因、限制及風險，而不是單純翻譯程式碼。
9. 不得為了滿足註解要求而對每一行程式碼加入註解。

---

## 九、必須加入註解的位置

以下內容必須視複雜度加入繁體中文註解：

1. 類別、介面及重要模組的用途。
2. 公開方法的主要目的。
3. 重要方法的輸入、輸出及副作用。
4. 複雜商業規則。
5. 不容易直接理解的條件判斷。
6. SQLite 資料建立、修改、刪除與清理邏輯。
7. Neo4j 節點、關係、索引及約束操作。
8. 測試資料建立及清理流程。
9. PAT 保留、遮罩、加密及防止誤刪的邏輯。
10. 具有資料刪除或外部副作用的操作。
11. 背景工作啟動、停止及取消流程。
12. 非直覺的演算法或資料流程。
13. 為了安全性、效能、相容性或框架限制所採用的特殊寫法。
14. 暫時性方案及已知限制。
15. 容易被未來維護者誤改的關鍵程式碼。
16. 測試結束後必須執行的資料清理。
17. 為避免誤刪 PAT 而採用的排除邏輯。
18. 清空 Neo4j 或測試目錄等破壞性操作前的環境檢查。

註解應優先說明：

* 為什麼這樣做。
* 為什麼不能使用更直覺的方式。
* 有哪些安全限制。
* 哪些資料必須保留。
* 哪些副作用需要注意。
* 哪些操作只允許在開發或測試環境執行。

---

## 十、不需要加入註解的位置

以下內容不應機械式加入註解：

1. 一看就能理解的變數指定。
2. 單純的 Getter 或 Setter。
3. 明顯的條件判斷。
4. 簡單的 null 檢查。
5. 每一行程式碼的中文翻譯。
6. 與方法或變數名稱完全重複的說明。
7. 沒有提供額外資訊的制式註解。
8. 為了增加註解數量而撰寫的無效內容。
9. 可以透過改善命名解決的可讀性問題。
10. 沒有特殊限制的標準框架設定。

錯誤範例：

```csharp
// 將 count 加一
count++;
```

較佳範例：

```csharp
// 限制單次測試呼叫 LLM 的次數，避免測試失敗時持續重試並產生額外費用。
requestCount++;
```

## 十一、C# XML Documentation 規則

對外公開或跨模組使用的 C# 類別、介面、方法及重要屬性，應視需要加入繁體中文 XML Documentation。

```csharp
/// <summary>
/// 清除 SQLite 中的測試資料，但保留人工問答功能所需的既有 PAT。
/// </summary>
/// <param name="cancellationToken">用於取消非同步清理作業的權杖。</param>
/// <returns>代表非同步清理工作的 Task。</returns>
public Task CleanupTestDataAsync(
    CancellationToken cancellationToken)
{
    // 實作內容
}
```

不需要為所有 private 方法機械式加入 XML Documentation。

private 方法只有在以下情況需要補充說明：

* 用途不容易從名稱理解。
* 存在重要副作用。
* 包含資料刪除。
* 包含安全限制。
* 包含複雜商業規則。
* 包含非直覺的處理流程。
* 可能影響 PAT 或其他 Credential。
* 僅允許在測試環境執行。

# 第四部分：錯誤處理與安全性

## 十二、錯誤處理

1. 不得使用空的 `catch` 區塊吞掉例外。
2. 不得記錄例外後假裝操作成功。
3. 錯誤訊息必須指出：

   * 哪個操作失敗
   * 失敗原因
   * 可能造成的影響
   * 是否可能留下測試資料
4. 不要為所有方法加入沒有處理價值的 `try-catch`。
5. 只有在能夠執行以下工作時才捕捉例外：

   * 補充錯誤脈絡
   * 轉換為領域錯誤
   * 執行補償
   * 執行安全清理
   * 釋放資源
6. 重新拋出例外時，必須保留原始 Stack Trace。
7. 包裝例外時，必須保留原始例外作為 Inner Exception。
8. 清理失敗時，必須明確回報可能殘留的資料或檔案。
9. 不得在例外或 Log 中輸出完整 PAT 或 Authorization Header。
10. 清理部分成功、部分失敗時，不得回報為完整成功。
11. SQLite、Neo4j 或測試目錄清理失敗時，必須分別回報。
12. 錯誤處理不得掩蓋人工問答功能所需 PAT 已遺失或損壞的情況。

---

## 十三、機密資訊規則

PAT、Token、API Key、Authorization Header 及其他 Credential 必須視為機密資訊。

不得將機密資訊寫入：

* 原始碼
* SVN
* Git
* Log
* Exception Message
* 測試報告
* Snapshot
* 測試資料
* 畫面截圖
* Request Dump
* Response Dump

必要時只能顯示遮罩後的值，例如：

```text
************A1B2
```

其他要求：

1. PAT 必須使用現有安全儲存機制保存。
2. 不得建立假的 PAT 覆寫人工測試使用的既有 PAT。
3. 不得在測試清理時刪除 PAT。
4. 不得將 PAT 複製到其他測試資料表。
5. 不得將 PAT 傳入不必要的服務。
6. 測試失敗時，也不得輸出完整 Credential。
7. 記錄 HTTP Header 時，必須移除或遮罩 Authorization。
8. 不得透過序列化整個設定物件的方式間接輸出 PAT。
9. 不得將真實 PAT 寫入測試程式碼或測試固定資料。
10. 測試結束後必須確認既有 PAT 仍可供人工問答功能使用。

# 第五部分：測試環境安全規則

## 十四、環境邊界

所有資料刪除及破壞性測試，只能在以下環境執行：

* Local
* Development
* Test
* 明確標示的 Integration Test Environment

執行刪除前，必須檢查：

1. 目前環境名稱。
2. SQLite 路徑。
3. Neo4j 連線位置。
4. 是否為本機或專用測試資料庫。
5. 是否存在明確的測試模式設定。
6. 是否可能連到正式或共用環境。
7. 測試檔案目錄是否為：
   `D:\Modern-Wingman\Modern-Wingman\temp`

如果無法確認環境安全，不得執行：

* 全資料庫清空
* Drop Table
* Drop Database
* Neo4j 全節點刪除
* 索引或約束刪除
* 測試目錄清空
* 任何不可逆的資料刪除

禁止操作：

* Production
* Staging
* 共用測試資料庫
* 公司正式資料
* 真實客戶資料
* 真實交易資料
* 真實帳務資料
* 未確認用途的遠端資料庫
* `D:\Modern-Wingman\Modern-Wingman\temp` 以外的目錄

環境判斷不得只依靠單一可被誤設的設定值。進行破壞性操作前，應同時確認環境名稱與實際連線或路徑。

# 第六部分：SQLite 規則

## 十五、SQLite 測試規則

1. 測試開始前，必須清除前一次測試遺留的資料。
2. 測試完成後，必須清除本次測試建立的所有資料。
3. 測試失敗、逾時、取消或拋出例外時，仍必須執行清理。
4. SQLite 中唯一允許保留的是人工問答功能所需的既有 PAT 或 Credential。
5. 不得刪除、修改、覆寫或建立假的 PAT。
6. 不得在清理過程中重新產生 PAT。
7. 清理邏輯必須明確排除 PAT 或 Credential。
8. 不得使用「先清空所有資料，再重新寫回 PAT」作為預設清理方式。
9. 應優先保留原有 PAT 紀錄，避免加密資料、建立時間或相關 Metadata 遺失。
10. 清理完成後，必須驗證除 PAT 或 Credential 外的資料皆已清除。
11. SQLite Schema 或 Migration 變更不得使既有 PAT 無法讀取。
12. 若 Credential Schema 必須破壞性重建，必須先設計安全的保留或遷移方式。

   * 節點數為零
   * 關係數為零

7. Neo4j Schema 初始化必須可以重複執行。

11. 清理前必須停止仍可能寫入 Neo4j 的背景工作。
12. 清理完成後必須避免背景工作重新寫回資料。
13. Neo4j 清理失敗時，不得宣告測試已完整完成。
14. 新增索引或約束必須有實際查詢需求，不得預先建立沒有使用到的索引。

# 第八部分：測試生命週期

## 十七、標準測試流程

所有整合測試及端對端測試應依序執行：

1. 確認目前為安全測試環境。
2. 驗證 SQLite 及 Neo4j 的實際連線目標。
3. 驗證測試檔案目錄為：
   `D:\Modern-Wingman\Modern-Wingman\temp`
4. 停止或隔離可能寫入資料的背景工作。
5. 清除上一次測試殘留的 SQLite 資料。
6. 清除上一次測試殘留的 Neo4j 節點及關係。
7. 清空測試檔案目錄。
8. 建立本次測試所需的資料。
9. 執行測試。
10. 收集必要的測試結果。
11. 在 `finally`、teardown 或等效機制中執行清理。
12. 停止並等待所有背景工作結束。
13. 清除 SQLite 中除既有 PAT 或 Credential 外的資料。
14. 清除 Neo4j 中所有節點與關係。
15. 清空測試檔案目錄。
16. 驗證不存在殘留資料或檔案。
17. 驗證既有 PAT 仍然存在。
18. 驗證應用程式可以重新啟動。
19. 驗證人工問答功能可以正常使用。

清理程序不得只在測試成功時執行。

* 測試逾時

* Neo4j 操作失敗
* SQLite 操作失敗
* 背景工作失敗
* 應用程式啟動失敗
* 測試中途終止
